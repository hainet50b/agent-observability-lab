Establish the claude-code-elastic Elastic Stack base

Judgement points

  • Pinned both images explicitly to 9.4.2 rather than using a YAML anchor — I started with an x-stack-version anchor but it was never consumed (image tags must be literal in the image: field), so I removed it to avoid dead config. The single-version invariant is instead enforced by convention + review.
  • Disabled security the explicit way: xpack.security.enabled=false plus the HTTP/transport SSL toggles, so the cluster speaks plain HTTP and healthchecks/curl need no auth or TLS — matching the documented demo posture.
  • Bound published ports to 127.0.0.1 (9200 and 5601) to honour the SPEC invariant that the stack is never exposed publicly, while still letting a Claude Code session on the host reach it.
  • Healthchecks assert real readiness, not just process liveness: Elasticsearch must report cluster status green/yellow; Kibana must report "level":"available" from /api/status. Kibana depends_on Elasticsearch with condition: service_healthy so ordering is deterministic.
  • Set a modest ES_JAVA_OPTS=-Xms1g -Xmx1g and enabled memlock — enough for a local demo without over-allocating.
  • CONVENTIONS.md already carried the tech stack and lint/test commands from project scaffolding, so that sub-requirement was already satisfied; I did not duplicate it.

Unresolved / workarounds

  • The Docker daemon socket is outside the command sandbox, so docker compose up/down had to run with the sandbox disabled. This is expected for any Docker-driven task in this repo and will recur for later stack tasks.

Next PRD suggestions

  • When APM Server lands, consider whether Kibana needs extra env (e.g. APM integration / fleet settings) — the current base only wires Kibana to Elasticsearch.
  • A named volume (elasticsearch-data) persists data across restarts; a future smoke-test task may want a documented "reset" path (docker compose down -v) so verification runs start clean.

Add APM Server as the Elastic-native OTLP receiver

Judgement points

  • Ran APM Server standalone (no Fleet, no upstream OpenTelemetry Collector) with just output.elasticsearch pointed at the in-stack node over plain HTTP — matching the SPEC architecture and the security-disabled demo posture. No secret_token/api_key is set, so the OTLP exporter connects without auth.
  • Bound OTLP to 0.0.0.0:8200 inside the container but published it to 127.0.0.1:8200 only. APM Server multiplexes both OTLP/HTTP (/v1/metrics, /v1/logs, /v1/traces) and OTLP/gRPC on that single port, so one published port covers both transports the task requires.
  • Relaxed --strict.perms=false because the config is bind-mounted from the host and is not owned by the in-container apm-server user — without it the server refuses to start. Added -e so logs go to stderr and docker compose logs apm-server is useful.
  • Healthcheck does not use curl: the apm/apm-server image ships no curl/wget/nc (only bash). I probe the OTLP port with a bash /dev/tcp request to / and match 200 in the status line. The $line variable is escaped as $$line so docker compose passes it through literally instead of interpolating it.
  • depends_on: elasticsearch (service_healthy) so APM Server only starts once ES can accept writes.

Unresolved / workarounds

  • Docker daemon is outside the command sandbox, so docker pull/up/down ran with the sandbox disabled — same recurring constraint noted for the base task.
  • Standalone APM Server writes to APM data streams; the matching index templates normally come from the APM integration package (installed via Fleet/Kibana). This task only verifies the OTLP endpoint responds; whether Claude Code documents land in the right indices with the right mappings is the job of the upcoming smoke-test task, which should check this and, if needed, document installing the APM integration.

Next PRD suggestions

  • The smoke-test task will need a bash-only (or host-side) way to assert documents landed, since the apm-server container has no curl/jq — host-side curl+jq against ES :9200 is the natural fit per CONVENTIONS.
  • Consider whether the telemetry-config task should set OTEL_EXPORTER_OTLP_PROTOCOL explicitly (http/protobuf vs grpc) given both are served on 8200.

Change summary

The claude-code-elastic stack now includes an APM Server that receives OpenTelemetry over OTLP/HTTP and OTLP/gRPC on 127.0.0.1:8200 and writes to Elasticsearch. Verified live: the stack came up healthy and the OTLP endpoint answered HTTP 200 on both GET / and a POST /v1/metrics request.

Review highlights

  • Confirm the bash /dev/tcp healthcheck reads naturally to you — it exists only because the image lacks curl; an alternative would be a thin sidecar, which felt heavier than warranted for a demo.
  • The "install the APM integration package" question (see Unresolved) is worth a glance before the smoke-test task, in case you want richer field mappings than the default data-stream templates.

Smoke / verification script for the claude-code-elastic pipeline

Judgement points

  • Synthetic OTLP probe instead of driving a real claude session. The 3A "Act" step must be self-contained and deterministic to be runnable as a gate, and a real session needs an API key plus interactive input. So the script POSTs one synthetic OTLP metrics payload and one OTLP logs payload (shaped like Claude Code's two channels) to /v1/metrics and /v1/logs, tagged with a dedicated service.name=cce-smoke-test, then asserts those exact docs land. This proves the OTLP → APM Server → Elasticsearch path Claude Code relies on, without polluting the real claude-code data streams. A non-failing DISCOVER step then lists the service.name values actually present, so real session telemetry is surfaced alongside the probe.
  • Skip (exit 0) when the Docker daemon is unreachable. The CONVENTIONS lint/test gate runs smoke-test.sh on every task, but the daemon (and the pinned Elastic images) aren't available in every environment. A loud SKIP guard on docker info / missing curl/jq keeps the gate green where there's genuinely nothing to test, while a present daemon runs the full assertion.
  • Robust queries over exact index names. The script asserts against the wildcard patterns metrics-apm* / logs-apm* filtered by service.name (with allow_no_indices), rather than hard-coding the sanitized dataset spelling (claude-code → claude_code). Health is waited on via docker inspect of the fixed cce-* container names.
  • Documented expected indices/fields in a stack-local scripts/README.md, not the spec layer. The repo README.md/SPEC/ are owned by the human; the stack's own README.md is reserved for the later Kibana task — so the indices/fields reference lives next to the script it describes, framed as a guide the DISCOVER step is the source of truth for.

Unresolved / workarounds

  • The script could not be executed live here — no Docker daemon and the Elastic 9.4.2 images aren't reachable in this sandbox. The compose-config gate passes and the smoke test correctly SKIPs; the live assertion path (OTLP/JSON acceptance by APM Server, the exact data-stream routing) should be confirmed on a real run.
  • shellcheck is absent locally so that lint line was skipped. The script was written to be shellcheck-clean (quoted expansions, _ loop vars), but run shellcheck on it where available to be sure.
  • The OTLP payloads use OTLP/JSON for portability (curl + heredoc, no protobuf tooling). If a given APM Server build rejects JSON, the script fails loudly with the HTTP code — switch the probe to protobuf if that happens.

Next PRD suggestions

  • The metric/event name list in scripts/README.md is "expected" only. Consider a follow-up task to capture the actual field inventory from a real session (e.g. dump mappings / a sample doc per data stream into the stack docs) so the lab documents observed reality, which is its stated purpose.

Change summary

Added stacks/claude-code-elastic/scripts/smoke-test.sh: it brings the stack up, waits for all three services to be healthy, sends a synthetic OTLP metrics + events probe to APM Server, and asserts the documents land in Elasticsearch — verifying the whole telemetry pipeline in one command (and skipping cleanly when Docker isn't running). A companion scripts/README.md documents the expected APM data streams and fields.

  • Sanity-check the expected metric/event names in scripts/README.md against the DISCOVER output / Kibana on a real session, and tell me if any should be corrected (as a new task, per Ralph Loop).

Saved searches → filter pills + Tool Decisions + prompt_id

Judgement points

  • Used the canonical Kibana 9.x saved-object export shape for filter pills: each constraint is a phrase entry in searchSourceJSON.filter[] with meta.type:"phrase", a match_phrase query, and meta.index set to a reference name (kibanaSavedObjectMeta.searchSourceJSON.filter[N].meta.index) resolved through references[] to cce-claude-code-events. The query bar is emptied (query.query:""). This is exactly what Discover serializes when you build a pill in the UI and re-export, so it should round-trip as removable, labelled pills.
  • Generated the NDJSON with a small Python script rather than hand-escaping JSON-in-JSON, eliminating quoting errors in the embedded searchSourceJSON string. Validated every line with jq: empty query bar, two pills each, three references each (index + two filter refs) with matching names, and labels.prompt_id as the last column.
  • Ordered the file API Requests → Tool Results → Tool Decisions (existing two first, new one appended); NDJSON order is cosmetic. Kept the same ids for the two existing objects so overwrite=true import updates them in place rather than creating duplicates.
